# 掲載審査ガイド

公開件数を増やすために未知を肯定しない。抽出は募集要項の整理に限定し、適合性は別の監査で判断する。

## 証拠

`evidence` の各要素に `id,field,url,quote_or_locator,checked_at,conclusion,method,notes` を記録する。有効期間のある根拠には `valid_through` も設定する（省略・nullは既知の失効日なし）。URLは `sources` にも登録し、実際に閲覧した日を付ける。長文の転載や個人情報は避ける。以下の `field` はすべて必須。

| field | 確認事項 |
|---|---|
| existence | 実在する企業の具体的な職種・応募ページ |
| employment | 当該募集枠が正社員であること |
| requirements_complete | 必須条件を網羅して読んだこと。歓迎要件と分離 |
| location | 実配属先が固定されていること。会社住所だけでは不可 |
| commute | 片道45分以内の経路実測、確実な地域内勤務、または完全在宅の居住条件 |
| recruitment | 現行募集の明示。単にURLが開けたという記録では不可 |
| reuse | 短い独自要約・リンクという再利用範囲に問題がないこと |

加えて、`eligibility.requirements` に下記の全観点を登録し、それぞれ同じ `field` の出典証拠を `evidence_ids` で参照する。

`graduated, graduation_date, education, it_years, employment_history, age, drivers_license, license_restriction, other_qualifications, relocation, travel, start_date`

制限がない観点も、募集要項を監査し「条件なし」を確認してから `operator=any` にする。単に書いてないように見えるだけ、未経験歓迎、先輩の入社事例だけでは既卒可・追加条件なしを断定しない。分からなければその観点を埋めずに保留を維持する。

| operator | 用途 |
|---|---|
| any | 当該属性への制限なしと確認済み。未知プロフィールでも属性値に依存しない |
| eq | 完全一致（boolと数値は区別） |
| gte / lte | 数値下限・上限（年数・年齢など） |
| in | 文字列などが許可リストに含まれる |
| between | `YYYY-MM` 等の文字列の範囲。卒業時期の上下限など |

`requirements_complete` をpassにする前に、観点にない必須条件も確認する。追加対応済みの `pc_basic, programming_basics, science_education` は必要な募集だけに登録し、確認済み属性と照合する。全求人の一律必須条件ではない。未対応の言語技能、専門経験、複数資格等を任意の新fieldにすると `unsupported_requirement` で保留になる。対応する型・プロフィール照合・テストを追加するか、直接確認後に監査手順を拡張する。研究・学習を企業の実務経験に換算しない。

## 判定と再確認

未知の本人属性が必要ならreview。確認済み属性が不一致、非正社員、45分超、募集終了・募集期限切れならrejected。固定勤務地・必要証拠の不足、日付不正、出典間の差異、必須証拠の有効期限切れはreview。ブラウザーでも非表示にする。

確認から30日超という経過日数だけでは非表示にしない。カード・詳細・一覧表・比較表に再確認警告と確認日を表示する。元の確認日は維持する。将来の日付、出典より新しい証拠などの不整合は引き続き公開を止める。卒業年度枠などの根拠には再確認期限を設定し、無期限の応募可能判定を避ける。これは企業の募集締切 `recruitment.valid_through` と区別する。

給与・休日・残業・在宅・転勤は希望条件であり、公開の必須条件に加えない。IT職種は現在の必須条件として審査・ブラウザー表示の両方で検査する。「歓迎」「尚可」を必須資格に変えない。ただし初期配属先が不明なら勤務地・通勤は保留する。

`python -m collector report` で非公開の個別審査台帳を生成する。IT職種と宮口周辺から確認順を並べる。任意の `data/internal/research-ledger.json` は各候補の `id,stage` を保持し、一覧での発見と詳細審査を分けて集計する。候補数を全件の適合確認済み件数として報告しない。実プロフィールがある場合のみ再照合し、プロフィール自体はレポートの公開出力に含めない。

日付を更新するだけで根拠を再確認した扱いにしない。ソースごとに実際に閲覧し、募集継続と条件を再確認する。異なる出典が矛盾するときはどちらが正しいかを確認し、解消した証跡を残して候補全体を再インポートする。自動統合された `duplicate-conflict` の除去だけでは解消にならない。

`review.jsonl` は `{job,reasons}` 形式なので、そのままインポートせず、編集した `job` オブジェクトの配列をJSONファイルとして再登録する。安定キーが一致するレビュー済み手動インポートは前回候補を置換する。職種・勤務地・採用区分が変更された場合は、古い候補を明示的に募集終了等で処理し、二重掲載を防ぐ。

## プライバシー

プロフィール値、内部の除外理由、元HTMLは公開エクスポートに含めない。公開される応募条件は雇用主が公表した条件だけ。証拠のnotes、自由記述、通勤前提に本人の氏名・詳細住所・年齢等を入れない。公開前に `jobs.json` 自体をレビューする。

## 保留候補の閲覧

応募可能枠は厳格な監査を維持する。一方、利用者の希望により、IT系の保留候補も別画面で公開する。公開前に `ReviewCandidate` の限られた項目へ手動編集し、内部証拠・本人プロフィール・自由記述を公開しない。具体的な原典、情報確認日、調査段階、残る確認事項が必須。募集終了や既知の条件不適合を保留候補として増やさない。

企業サイトの会社住所を勤務地として断定しない。研修・顧客先・複数拠点の条件は理由に記載する。検索や一覧で発見しただけなら詳細未確認と表示し、募集が現行と確認できた扱いにしない。期限が既知なら確認待ち側にも保持する。

## 確認待ちの条件表示

`ReviewCandidate.facts` は省略可能な条件配列。対応する `field` は `salary, location, employment, hours, holidays, commute`。値は短い要約 `text` と、その項目を確認した原典 `url`、実際の情報確認日 `checked_at` を記録する。対応する出典を `Job.sources` にも登録する。同じ項目の重複や候補確認日より未来の条件日付を認めない。内部プロフィールや審査メモは混ぜない。

給与内訳が分からなければ基本給と断定しない。年収を月給へ自動換算しない。モデル年収を初年度保証額にしない。学歴別初任給・手当・固定残業代・試用期間の違いを明記する。年間休日と計画有休、過去年度実績と現行条件を分ける。会社所在地だけなら実勤務地として確定しない。検索でしか読めない値、旧求人の値、募集継続未確認はその旨を値に注記する。
