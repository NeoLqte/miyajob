# 掲載審査ガイド

公開件数を増やすために未知を肯定しない。抽出は募集要項の整理に限定し、適合性は別の監査で判断する。

## 証拠

`evidence` の各要素に `id,field,url,quote_or_locator,checked_at,conclusion,method,notes` を記録する。URLは `sources` にも登録し、実際に閲覧した日を付ける。長文の転載や個人情報は避ける。以下の `field` はすべて必須。

| field | 確認事項 |
|---|---|
| existence | 実在する企業の具体的な職種・応募ページ |
| employment | 当該募集枠が正社員であること |
| requirements_complete | 必須条件を網羅して読んだこと。歓迎要件と分離 |
| location | 実配属先が固定されていること。会社住所だけでは不可 |
| commute | 片道45分以内の経路実測、確実な地域内勤務、または完全在宅の居住条件 |
| recruitment | 現行募集の明示。単にURLが開けたという記録では不可 |
| reuse | 短い独自要約・リンクという再利用範囲に問題がないこと |

加えて、`eligibility.requirements` に下記の全観点を登録し、それぞれ同じ `field` の出典証拠を `evidence_ids` で参照する。

`graduated, graduation_date, education, it_years, employment_history, age, drivers_license, license_restriction, other_qualifications, relocation, travel, start_date`

制限がない観点も、募集要項を監査し「条件なし」を確認してから `operator=any` にする。単に書いてないように見えるだけ、未経験歓迎、先輩の入社事例だけでは既卒可・追加条件なしを断定しない。分からなければその観点を埋めずに保留を維持する。

| operator | 用途 |
|---|---|
| any | 当該属性への制限なしと確認済み。未知プロフィールでも属性値に依存しない |
| eq | 完全一致（boolと数値は区別） |
| gte / lte | 数値下限・上限（年数・年齢など） |
| in | 文字列などが許可リストに含まれる |
| between | `YYYY-MM` 等の文字列の範囲。卒業時期の上下限など |

`requirements_complete` をpassにする前に、観点にない必須条件も確認する。現状で扱えない言語技能、専門経験、複数資格等は任意の新fieldを追加すると `unsupported_requirement` で保留になる。対応する型・プロフィール照合・テストを追加するか、直接確認後に監査手順を拡張する。既存観点に無理に押し込んでpassにしない。

## 判定と再確認

未知の本人属性が必要ならreview。確認済み属性が不一致、非正社員、45分超、募集終了ならrejected。固定勤務地・必要証拠の不足、日付不正、30日超の証拠、出典間の差異はreview。現在のブラウザー表示でも同様に検査する。

日付を更新するだけで根拠を再確認した扱いにしない。ソースごとに実際に閲覧し、募集継続と条件を再確認する。異なる出典が矛盾するときはどちらが正しいかを確認し、解消した証跡を残して候補全体を再インポートする。自動統合された `duplicate-conflict` の除去だけでは解消にならない。

`review.jsonl` は `{job,reasons}` 形式なので、そのままインポートせず、編集した `job` オブジェクトの配列をJSONファイルとして再登録する。安定キーが一致するレビュー済み手動インポートは前回候補を置換する。職種・勤務地・採用区分が変更された場合は、古い候補を明示的に募集終了等で処理し、二重掲載を防ぐ。

## プライバシー

プロフィール値、内部の除外理由、元HTMLは公開エクスポートに含めない。公開される応募条件は雇用主が公表した条件だけ。証拠のnotes、自由記述、通勤前提に本人の氏名・詳細住所・年齢等を入れない。公開前に `jobs.json` 自体をレビューする。
